# 面试问题：什么是 Query 改写

## 回答

Query 改写是指：在不改变用户真实意图的前提下，把用户的原始输入转换成更适合检索、数据库查询或工具调用的表达。

用户输入通常是面向人类交流的，可能包含指代、省略、口语噪声、相对时间和模糊实体；而下游系统需要明确、稳定、可执行的输入。因此，Query 改写的本质是缩小用户语言与检索系统或工具接口之间的表达差异。

例如：

```text
对话历史：用户正在询问 Redis。
当前问题：它支持什么持久化方式？

改写结果：Redis 支持什么持久化方式？
```

这里不是让句子更通顺，而是把一个依赖上下文的问题改写成能够独立检索的问题。

## 一、Query 改写通常位于什么位置

在企业 Agent 中，典型链路是：

```text
用户输入
-> 意图识别
-> Query 改写
-> 检索或工具调用
-> 结果重排
-> LLM 生成回答
```

常见应用场景包括：

1. RAG 知识库检索。
2. 多轮客服和问答。
3. 搜索引擎和企业文档搜索。
4. SQL、Elasticsearch 等结构化查询。
5. Agent 工具调用。
6. 外部模型调用前的隐私最小化。

## 二、为什么需要 Query 改写

### 1. 解决指代和省略

```text
历史：介绍一下 PostgreSQL。
用户：它怎么做高可用？
改写：PostgreSQL 怎么实现高可用？
```

### 2. 提高检索召回率

用户的口语表达可能和企业文档术语不同：

```text
用户表达：重复扣钱怎么办
企业术语：重复扣款、重复支付、重复交易
```

通过标准化或同义词扩展，可以提高相关文档被召回的概率。

### 3. 转换为工具可执行参数

```text
用户：帮我总结寻徐上周的微信消息

结构化结果：
{
  "contact": "寻徐",
  "start_date": "2026-06-01",
  "end_date": "2026-06-07"
}
```

### 4. 降低噪声、成本和误检

```text
原查询：麻烦帮我认真看看公司报销到底需要准备哪些东西，谢谢
改写：公司报销需要准备哪些材料
```

### 5. 保护敏感信息

在调用外部搜索或模型前，可以删除与任务无关的身份证号、手机号等敏感信息，只保留完成任务所需的查询内容。

## 三、常见的改写方式

### 1. 指代消解与上下文补全

将依赖历史的问题改写为独立问题：

```text
历史：介绍一下 Redis。
当前问题：它支持什么持久化方式？
改写：Redis 支持什么持久化方式？
```

如果历史中同时出现多个候选对象，系统不应该擅自选择，而应向用户澄清：

```json
{
  "needs_clarification": true,
  "clarification_question": "你想了解 Redis、MySQL 还是 PostgreSQL 的优点？"
}
```

`clarification_question` 是信息不足或指代不明确时，Agent 返回给用户的澄清问题，不是最终答案。

### 2. 关键词提取与去噪

删除礼貌、情绪和重复表达，保留检索核心：

```text
原查询：麻烦帮我认真看看公司报销到底需要准备哪些材料，谢谢
去噪查询：公司报销需要准备哪些材料
关键词：公司报销、材料
```

去噪时必须保留否定、时间、数字和版本：

```text
原查询：请找最近 30 天 Python 3.11 中不使用 Redis 的缓存实现
去噪查询：最近 30 天 Python 3.11 中不使用 Redis 的缓存实现
```

如果误删“不”，检索意图会完全相反。

### 3. 同义词和领域术语扩展

```text
重复扣钱
-> 重复扣款、重复支付、重复交易
```

企业中可以结合术语词典、搜索点击数据和 LLM 完成扩展。扩展词应与用户原始词分开记录，避免无法判断信息来源。

### 4. 时间、单位和实体标准化

```text
用户：查一下上周华东区 GMV

标准化结果：
{
  "metric": "gross_merchandise_value",
  "region": "east_china",
  "start_date": "2026-06-01",
  "end_date": "2026-06-07"
}
```

日期计算、金额和单位换算等确定性任务，应优先由代码完成，而不是完全交给 LLM。

### 5. 结构化改写

把自然语言转换成受约束的中间表示：

```json
{
  "intent": "query_orders",
  "filters": {
    "status": "refunded",
    "date_range": "last_month"
  },
  "group_by": "reason"
}
```

程序先校验字段，再生成 SQL、DSL 或工具参数。相比直接执行 LLM 生成的任意 SQL，这种方式更可控。

### 6. Query Decomposition

将复杂问题拆成多个子查询：

```text
原问题：对比 Redis 和 PostgreSQL 的持久化及高可用机制

子查询：
1. Redis 的持久化机制
2. Redis 的高可用机制
3. PostgreSQL 的持久化机制
4. PostgreSQL 的高可用机制
```

各子查询分别检索，最后合并和重排。它适合复杂对比和多跳问题，但会增加延迟和调用成本。

### 7. Multi-Query

针对同一意图生成多个查询表达，并行召回：

```text
Agent 幻觉的治理方法
RAG 如何减少模型事实错误
工具调用结果如何进行事实校验
```

召回结果可以按文档 ID 去重，再通过 RRF 或 Reranker 合并排序。

### 8. HyDE

先生成一段假设性答案或理想文档，再对该文本做 embedding 检索。它可以缩小短问题与长文档之间的语义表达差异。

HyDE 生成的内容只用于检索，不能直接当作事实答案。

### 9. Step-back Query

把具体问题抽象为更通用的原理问题：

```text
具体问题：为什么 X25519 握手后还要使用 HKDF？
抽象问题：密钥交换后为什么需要密钥派生函数？
```

通常同时检索原始 Query 和抽象 Query，以获得实现细节和背景原理。

## 四、为什么经常让 LLM 输出 JSON

Query 改写并不一定要输出 JSON。

如果下游只需要一个改写后的查询，直接输出文本更简单：

```text
Redis 支持什么持久化方式？
```

当 Agent 还需要流程控制、审计或多路检索输入时，结构化输出更合适：

```json
{
  "standalone_query": "Redis 支持什么持久化方式？",
  "used_history": true,
  "confidence": 0.98,
  "needs_clarification": false,
  "clarification_question": ""
}
```

JSON 的主要价值是：

1. 支持“检索还是追问”等流程分支。
2. 可以校验必填字段和数据类型。
3. 可以记录模型使用了哪些历史、删除了哪些噪声。
4. 可以同时为向量检索和 BM25 提供不同输入。
5. 便于后续扩展过滤条件、置信度等字段。

选择原则是：

```text
只需要一个 Query
-> 直接输出文本

需要多个结果或流程分支
-> JSON 或 Structured Output

需要调用工具
-> Function Calling 或 Tool Calling

需要严格约束
-> JSON Schema + 本地校验
```

## 五、LLM 输出 JSON 不稳定怎么办

不能默认相信 LLM 输出。生产系统通常采用多层防护：

1. 优先使用模型提供的 JSON Mode、Structured Output 或 Tool Calling。
2. 使用 JSON Schema 或 Pydantic 校验字段类型和必填项。
3. 兼容 Markdown 代码块等常见模型输出。
4. 解析失败后，将错误原因反馈给模型，限制重试一到两次。
5. 多次失败后使用原始 Query 降级，或者停止高风险工具调用。
6. 记录解析成功率、重试率和降级率。

Prompt 不能只给字段名，还要说明：

- 每个字段的业务含义。
- 字段之间的联动规则。
- 哪些信息可以补全，哪些信息不能猜测。
- 正常情况和歧义情况的示例。

例如：

```text
needs_clarification=true
-> clarification_question 不能为空
-> standalone_query 保留原始问题

needs_clarification=false
-> clarification_question 必须为空字符串
```

## 六、企业中的典型实现

```text
原始 Query
-> 指代消解与上下文补全
-> 实体、时间和单位标准化
-> 关键词提取与去噪
-> 根据复杂度选择单路、Multi-Query、Decomposition 或 HyDE
-> 原始 Query 与改写 Query 混合召回
-> 去重与 Rerank
```

工程上应遵循以下原则：

1. 规则和代码处理确定性信息，LLM 处理语义信息。
2. 始终保留原始 Query，防止错误改写导致召回完全丢失。
3. 不确定时追问，不允许模型自行补充关键事实。
4. 对否定、时间、数字和版本做额外校验。
5. 使用离线数据集和线上指标评估改写收益。

常见评估指标包括：

- Recall@K。
- Precision@K。
- MRR。
- nDCG。
- JSON 解析成功率。
- 澄清触发准确率。
- 最终任务成功率。
- 改写引入错误条件的比例。

## 七、本项目如何进行 Query 改写

本项目目前存在两种路径。

### 微信活动报告

微信报告工具使用显式的结构化改写：

```text
route_intent
-> parse_request
-> resolve_contact
-> build_report
-> final_response
```

`parse_request` 会从当前输入和 Redis 短期历史中提取：

- 联系人或群名。
- 时间范围。
- account、username 等显式参数。
- 输出目录和报告选项。

例如：

```text
用户：帮我生成和寻徐的活动总结
助手：还需要时间范围
用户：今天
```

系统会从历史中补回“寻徐”，将“今天”转换为明确的开始和结束时间戳，再把展示名称解析为微信 API 使用的 `username`。

这里的 Query 改写本质上是把口语请求转换为确定的 Tool Call。

### 长期记忆检索

普通对话当前没有显式 Query Rewrite。系统基本直接把用户原始消息传给 Vault，使用 `text-embedding-v4` 生成查询向量，再与 active 记忆做相似度检索。

因此，准确地说：

> 本项目已经为微信工具实现了规则式、多轮、结构化 Query 改写，但长期记忆 RAG 目前仍以原始 Query 直接检索为主。

后续可以在长期记忆检索前加入受约束的 Rewrite 节点，通过“原始 Query + 改写 Query”双路召回，解决“他喜欢什么”“那个目标完成了吗”之类的指代问题，同时降低改写偏离意图的风险。

## 总结

Query 改写不是单纯的文本润色，而是 Agent 在自然语言和检索、数据库、工具接口之间建立的一层语义适配。

一个可靠的改写系统应该做到：

> 该补全的上下文要补全，该保留的约束不能删除，不确定的信息不能猜测，原始 Query 必须保留，改写效果必须通过检索和任务指标验证。
