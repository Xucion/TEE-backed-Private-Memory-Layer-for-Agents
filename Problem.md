# Memory Pollution Problem

## Background

This project implements a command-line chat application with LangGraph, Alibaba Cloud Tongyi, and a local encrypted long-term memory store.

The intended memory behavior is:

- Extract stable user facts or explicit user preferences from conversation.
- Store extracted memories locally in encrypted form.
- Retrieve relevant memories in later turns to improve the assistant's responses.

During testing, a problem appeared after three conversation turns:

1. The user said they have diabetes.
2. The user asked for diet recommendations.
3. The user said they wanted to drink porridge.

After decrypting the memory store, the following kinds of memories appeared:

- Valid user fact: the user has diabetes.
- Valid or partially valid user intent: the user needs diet recommendations.
- Valid but possibly temporary user preference/request: the user wants porridge.
- Invalid memories: assistant-generated advice such as choosing multigrain porridge, avoiding white rice porridge, making porridge thicker, adding vegetables or lean meat, and controlling intake.

The invalid memories are not user facts. They are recommendations generated by the assistant. Storing them as long-term user memory pollutes the memory store.

## Root Cause

The problem had two connected causes.

## 1. Assistant Replies Were Treated As Memory Sources

Before the fix, `chat_app.py` passed both the latest user message and the assistant reply into the memory extractor:

```python
args=([HumanMessage(content=user_input), reply],)
```

Then `memory_extractor.py` serialized both `HumanMessage` and `AIMessage` into the extraction prompt:

```python
if isinstance(msg, HumanMessage):
    conv_text += f"用户: {msg.content}\n"
elif isinstance(msg, AIMessage):
    conv_text += f"助手: {msg.content}\n"
```

The extractor prompt said to extract useful long-term user information, but it did not strongly prohibit extracting from assistant messages. As a result, the model could interpret assistant advice as memory-worthy information.

Example:

- User says: "我想喝粥"
- Assistant replies: "建议选择杂粮粥，避免白米粥，控制摄入量..."
- Extractor stores: "建议选择杂粮粥..." as if it were user memory

This is wrong because the memory came from the assistant, not from the user.

## 2. History Influenced The Assistant Reply, Then The Reply Polluted Memory

The extractor was not directly receiving the full conversation history. However, the chat model did receive conversation history when generating the assistant reply.

That means earlier facts, such as "用户有糖尿病", influenced the assistant's third-turn response about porridge. The assistant gave diabetes-aware advice. Then the extractor saw that assistant response and stored parts of it as long-term memory.

So the pollution path was:

```text
old user memory -> assistant response -> extractor -> new stored memory
```

This creates a feedback loop:

1. A memory affects a future answer.
2. The future answer is extracted as new memory.
3. The new memory affects later answers.
4. The memory store gradually fills with model-generated advice instead of user-authored facts.

## Why This Is A Serious Problem

This issue is serious because long-term memory should represent the user, not the assistant.

If assistant-generated content is stored as user memory, several bad things can happen:

- The system may treat one-time suggestions as stable user preferences.
- The memory store may become noisy and less useful.
- Retrieval may surface irrelevant or misleading memories.
- Model outputs may become increasingly self-referential.
- Sensitive topics may accumulate more derived information than the user explicitly provided.

In the diabetes example, it is reasonable to store "用户有糖尿病" because the user explicitly said it. It is not reasonable to store "建议选择杂粮粥" as a user memory because that is the assistant's recommendation.

## Is This A Common Problem?

Yes. This is a common class of problem in memory-enabled LLM systems.

Common names or related concepts include:

- Memory pollution
- Memory contamination
- Self-generated memory
- Assistant-output feedback loop
- Derived fact pollution
- Source attribution failure

The core issue is that a system fails to distinguish between:

- Facts stated by the user
- Preferences explicitly stated by the user
- Temporary user requests
- Assistant suggestions
- Assistant inferences
- Retrieved context injected into the prompt

Memory systems usually need strict boundaries around what is eligible for storage. Without those boundaries, model-generated text can easily leak back into memory.

## Fix Applied

The fix uses two layers:

- Source control: only pass user-authored messages to the extractor.
- Output filtering: only accept extractor results that claim the source is the user.

## 1. Only Pass User Messages To The Extractor

`chat_app.py` was changed from passing both the user message and assistant reply:

```python
args=([HumanMessage(content=user_input), reply],)
```

to passing only the user message:

```python
args=([HumanMessage(content=user_input)],)
```

This prevents assistant recommendations from entering the extractor prompt at all.

## 2. Tighten The Extractor Prompt

`memory_extractor.py` now tells the model to extract only from user-authored text:

```text
分析以下用户原话，提取值得长期记忆的用户信息。
只从“用户原话”中提取客观事实或明确偏好，不要从助手回复、建议、推断或临时任务中提取。
不要保存一次性请求，例如“帮我推荐饮食”“我想喝粥”，除非用户明确表达这是长期偏好。
```

The prompt also asks for a `source` field:

```json
{
  "content": "记忆内容",
  "category": "health | preference | business | other",
  "sensitivity": "high | low",
  "source": "user"
}
```

This makes source attribution explicit.

## 3. Filter Model Output In Code

`memory_extractor.py` now normalizes and filters model output with `_normalize_memories()`.

The filter:

- Drops non-dictionary items.
- Drops empty memory content.
- Normalizes unknown categories to `other`.
- Normalizes unknown sensitivity values to `low`.
- Drops any memory whose `source` is not `user`.
- Removes the `source` field before storage, keeping the existing memory schema simple.

This is important because prompts are guidance, not guarantees. Code-level validation is still needed.

## Is This A Common Solution?

Yes. The fix follows common memory-system design practice.

Common mitigation patterns include:

- Source gating: only user messages are eligible for memory extraction.
- Role-aware extraction: assistant messages may be used as context, but not as sources.
- Structured output: extracted memories include fields like `source`, `category`, and `sensitivity`.
- Post-extraction validation: code filters invalid or unsafe outputs before storage.
- Stable-memory criteria: store durable facts and explicit preferences, not temporary tasks or assistant advice.

This project now uses the first, third, fourth, and fifth patterns. It avoids using assistant messages as extraction input, which is the simplest and safest approach for the current prototype.

## Remaining Limitations

The current fix prevents new assistant-generated advice from being stored, but it does not automatically clean old polluted memories from `memories.enc`.

Existing invalid memories such as assistant recommendations should be removed manually or with a cleanup script.

The system also still relies on the model to decide whether a user statement is a stable long-term memory. For example:

- "我有糖尿病" should be stored.
- "我喜欢喝粥" may be stored as a preference.
- "我想喝粥" is probably a temporary request and should usually not be stored.

Future improvements could include:

- A stricter rule-based filter for temporary requests.
- A cleanup script for old polluted memories.
- Explicit user confirmation before storing high-sensitivity memories.
- More precise source metadata in the stored memory schema.
- A memory review UI or command-line approval flow.

## Summary

The issue was not simply that the extractor saw too much text. The deeper issue was that assistant-generated content was allowed to become long-term memory.

The fix was to enforce a cleaner memory boundary:

```text
Only user-authored stable facts and explicit preferences can become long-term memory.
Assistant replies, recommendations, inferred facts, and temporary requests should not be stored.
```

This is a common problem in LLM memory systems, and the applied fix is also a common and recommended pattern: source-gated extraction plus structured validation.
